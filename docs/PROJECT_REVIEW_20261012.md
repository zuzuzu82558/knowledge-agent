# 项目复查：2026-10-12

结论：项目适合作为单人本地使用、可追溯的 RAG 工作台原型。版本/代次隔离、来源追踪、失败状态和离线测试基础较扎实，但本次确认了四个现有测试没有覆盖的问题，其中两个会意外切换当前文档版本。建议先修复版本发布逻辑和证据预算，再投入新的 Agent 或图谱功能。现有验证不足以证明真实问答质量或多人生产可用性。

本次检查覆盖 API、文档摄入/版本/重试/删除、SQLite 和向量索引、检索/上下文/缓存、模型预算、联网工具、全文洞察、图谱、前端主要交互、评测与部署说明。没有修改应用代码或业务数据，没有读取密钥内容，也没有调用付费模型或真实搜索。复现使用隔离存储和明确的测试替身。

## 已确认问题

### R1 · P1：普通重复上传会把当前文档切回旧版本

位置：`app/service.py:110`、`app/service.py:130–133`。

操作顺序：上传收入为 100 万元的 A 版 → 显式更新为收入 300 万元的 B 版 → 在“上传新文档”入口再次上传 A，且不传 `document_id`。

实际结果：代码从所有历史版本中匹配到原文档，将 A 的已完成代次重新写入 `documents.active`，返回 `idempotent=true`。UI 提示“文件已存在，复用已有版本”，但之后问答实际使用 A。B 的文件仍在，问题是活动版本被无提示回退，并非物理文件被删除。

原因：内容去重与切换活动版本混在同一条路径；“命中已完成任务”被当作切换当前版本的授权。

修复方向：区分普通去重上传、显式版本更新和历史版本切换。普通去重命中历史内容不应修改已有文档的活动版本；若产品需要回退，应有独立、可见的操作语义。

复现：`artifacts/review-20261012/test_review_probes.py::test_new_upload_of_historical_content_silently_rolls_back_existing_document`。

### R2 · P1：重试过期的失败任务会覆盖后续成功版本

位置：`app/service.py:226–237`、`app/service.py:199–200`。

操作顺序：A 摄入成功 → B 因索引写入故障失败 → 上传 C 并成功发布 → 从处理记录重试 B。

实际结果：B 重试成功后无条件设置为活动代次。复现中 C 的收入 300 万元退回 B 的 200 万元，下一次问答读取 B。旧失败任务仍可通过历史处理记录重试。

原因：重试只校验任务状态、文档是否删除及配置是否一致，不校验该任务是否已被更新的版本取代；发布时没有条件更新。

修复方向：记录文档最新的发布意图/目标代次，在完成时进行条件更新。过期任务可选择拒绝重试，或允许修复历史索引但不自动发布。只比较“完成时间”不能解决问题，因为旧任务重试恰好会最后完成。

复现：`artifacts/review-20261012/test_review_probes.py::test_retry_obsolete_failed_version_replaces_newer_active_version`。

### R3 · P2：默认混合证据预算会排除所有已读取网页

位置：`app/context.py:55–59`、`app/context.py:76–87`；混合候选由 `app/online.py` 按文档/网页交错排列。

复现采用默认 `EVIDENCE_BUDGET_BYTES=3000`、`RETRIEVAL_TOP_K=8`、候选池 24：20 条文档候选与 5 个已成功读取的网页交错排列。网页使用正常长度标题和 URL。

实际结果：最终入选 8 条文档、0 条网页；5 条网页全部标为 `context_budget`。网页最小证据约 423 字节，但每轮平均分配只有约 374–393 字节。较小的文档元数据能够通过，较大的网页元数据被逐条跳过，即便重新分配总预算完全可以容纳文档与网页两类证据。

影响：“资料 + 联网”会支付搜索/阅读成本，却可能完全不用已读网页回答。排序并非唯一决定因素，元数据大小在这里形成了隐含的来源偏好。该问题不意味着每次混合查询都会失败，也不意味着未选网页仍被模型引用。

修复方向：先计算候选的最小元数据与正文成本，再决定可容纳的证据数量和来源配额；按来源保留最低可用预算，然后分配剩余正文预算。被平均份额拒绝的高排名候选应有重新分配机会，而不是直接永久跳过。

复现：`artifacts/review-20261012/test_review_probes.py::test_default_combined_budget_excludes_all_five_read_web_pages`。

### R4 · P2：全文洞察超时后，当前响应与历史记录丢失已完成部分

位置：`app/service.py:485–487`、`app/service.py:623–630`；章节结果在 `app/insights.py` 内部累计。

复现：两块文档，第一块模型摘要成功并写入 `summaries`，第二块调用超过整次任务截止时间。

实际结果：返回 `request_timeout`，`evidence=[]`、`claims=[]`，没有 `coverage`；数据库中已经有一条完成的摘要。通用超时分支只恢复普通检索/联网候选，拿不到全文洞察内部已经完成的结果。

影响：用户无法在这次响应或该次历史记录中看到已完成的摘要及来源，需要重新执行。已落盘的摘要检查点并未永久丢失，后续重试仍可复用。

修复方向：让全文洞察逐块向可恢复的结果对象提交进度，或在取消时返回已完成章节、证据、覆盖率及中断状态；不得把未完成块计入完整覆盖。

复现：`artifacts/review-20261012/test_review_probes.py::test_summary_timeout_discards_already_completed_section_evidence`。该测试使用 1 秒截止时间和合成模型响应，缩短真实长任务触发同一路径所需的等待。

## 整体判断与改进顺序

做得较好的部分：

- 内容版本、索引代次、历史引用分离；多数失败路径有明确状态，避免把模型失败包装成成功回答。
- 查询保留检索分支、融合、证据选择、模型调用和来源，便于核对。
- 联网读取有 URL/DNS/重定向/大小与时间限制；前端主要使用 `textContent`，原始文件按附件下载。这里仅记录代码检查结果，不等同于完整漏洞审计或依赖漏洞扫描。
- 当前离线测试和浏览器测试可重复执行；README 对“接口通过”与“真实质量通过”的区分较诚实。

需要正视的产品与工程边界：

- **真实效果证据不足。** 仓库有首次真实模型/搜索检查记录，但不等于系统性效果验收；本轮也没有新增真实服务验证。GraphRAG、重排、受控 Agent 是否提高正确率，仍需要独立人工核对和同预算对照。现有锚点匹配只衡量文字命中。
- **默认上下文偏小。** 3000 是 UTF-8 字节，包含元数据；对中文多来源问题，可用于正文的空间更少。全文聚合也受该预算限制。应根据真实样本调参和测量，不能仅通过增加检索候选数解决。
- **长任务会影响整个工作台。** 摄入、问答、删除、重建、图谱构建共享同一把服务锁。一次长摄入/全文洞察可能让后续问答在队列中超时。这是当前明确的单人架构取舍；若扩展多人使用，需要后台任务、进度/取消和更细的发布锁。
- **持久数据持续增长。** 历史代次、运行记录和网页快照没有统一的保留/清理策略；`/api/runs` 为列表反序列化完整结果，前端每 5 秒轮询。规模增大后需以真实数据量测磁盘、内存和轮询耗时，再增加摘要字段、索引和保留策略。此项是代码层面的风险判断，未做容量压测。
- **维护热点集中。** `Service._query` 同时承担路由、缓存、检索、联网、重排、生成、取消与持久化；前端也集中于单个脚本。建议随上述问题修复按职责拆分，不建议为了架构整洁重写整个项目。
- **当前目录没有 Git 仓库。** `.github/workflows` 已有配置，但本地不是 Git checkout，不能据此声称 CI 或版本回滚已经可用。后续应建立版本管理和备份流程；本次未擅自初始化或发布仓库。
- **部署目标仍是本机单实例。** 无认证、多租户、高可用是已知边界，不能将当前状态直接当作公网服务交付条件。

建议顺序：先统一活动版本发布规则，修 R1/R2；再修 R3/R4 并把复现转为正式回归；然后做代表性真实中文资料的效果验收。扩大 Agent/图谱功能之前，先证明它们能在同一问题集与预算下带来收益。
